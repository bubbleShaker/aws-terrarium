# シミュレーションを 3D で動かすときに知っておくこと (2026-08-01)

M2 の実装で使った、初見だと理由が分かりにくいパターンの解説。
モデルの話ではなく、**リアルタイム描画とシミュレーションを繋ぐときの定石**。

## Q. なぜ「フレームの経過秒」をそのままシミュレーションに渡してはいけないのか

渡すと、**同じ操作をしても毎回違う結果になる**から。

```ts
// ❌ これをやると決定論性が壊れる
useFrame((_, delta) => table.step(demand, delta));
```

`delta` はブラウザ任せで 16ms だったり 33ms だったりする。
シミュレーションの計算はステップ幅に依存するので（バーストの消費量、スロットルの判定…）、
ステップ幅が揺れれば結果も揺れる。
「同じ設定なら常に同じ結果」という M1 の土台がここで崩れる。

### 固定タイムステップの蓄積方式

実時間を**溜めて**、溜まった分だけ**常に同じ幅**で刻む。

```
accumulator += 実フレーム経過秒 × 時間倍率
while (accumulator >= 0.1) {
  table.step(demand, 0.1);   // ← 常に 0.1 秒。ここが揺れない
  accumulator -= 0.1;
}
```

1 秒ぶんの実時間は、60fps でも 20fps でも「0.1 秒の tick が 10 回」になる。
刻む**タイミング**は揺れるが、刻む**幅**は揺れない。これで結果が一致する。

### なぜ 1 フレームの tick 数に上限が要るのか

タブを裏に回すと `requestAnimationFrame` が止まり、戻ってきた瞬間に
「10 秒経過しました」という `delta` が来る。上限が無いと 100 tick を一気に回し、
その処理で次のフレームがさらに遅れ、もっと大きな `delta` が来る——という
**死のスパイラル**に入る。

上限に当たったぶんの時間は捨てる。つまり仮想時間が実時間から遅れることを許す。
「遅れを取り戻さない」ことが正解である場面が、リアルタイム描画には存在する。

## Q. なぜ毎フレーム React の state を更新してはいけないのか

`setState` は再描画を起こす。柱 50 本ぶんの props を組み立てて差分を取る処理が
60 回/秒 走ると、それだけでフレーム予算（16.6ms）を使い切る。

M2 では役割を分けた:

| | 更新頻度 | 経路 |
|---|---|---|
| 3D の柱・粒子 | 毎フレーム | `session.latest` を直接読み、three.js のオブジェクトを書き換える |
| HUD の数字 | 10Hz | `setState` で React に流す |

**React を経由しない**のがポイント。R3F の `useFrame` の中で
`mesh.position.set(...)` のように直接書き換えれば、React は何も知らないまま絵だけが動く。
数字は 10Hz もあれば人間には読めるので、そこだけ React に任せる。

## Q. `InstancedMesh` とは何か

**同じ形を大量に描くための仕組み**。柱 50 本を `<mesh>` 50 個で描くと、
GPU への描画命令が 50 回発行される（ドローコール 50 回）。
`InstancedMesh` なら「この箱を 50 個、それぞれこの位置・この色で」と**1 回**で伝えられる。

```ts
mesh.setMatrixAt(i, matrix);   // i 番目の位置・回転・拡大
mesh.setColorAt(i, color);     // i 番目の色
mesh.instanceMatrix.needsUpdate = true;  // ← これを忘れると何も変わらない
```

`needsUpdate = true` は「バッファを書き換えたので GPU に送り直して」の合図。
three.js は毎フレーム自動で送り直したりはしない（送る方が高いので）。

## Q. 粒子はどこまで「本物」なのか

**見た目だけ**。粒子はシミュレーションに一切影響しない。

- 数値（何 req/s が通り、何 req/s が弾かれたか）は Core が統計的に計算する
- 粒子はその統計を**表現するために** 420 個だけ描く。1 個 = 数十リクエストの代表

30,000 req/s を粒子 1 個ずつ描いたら即死する。
「統計値は正確なまま、絵だけ間引く」がこのプロジェクトの一貫した方針
（PLAN.md「なぜ tick ベースのハイブリッドか」）。

弾かれるかどうかは、着弾の瞬間にそのパーティションのスロットル率で抽選している。
たとえば 96% スロットル中の柱なら、粒子の 96% が赤く散る。
**確率としては正しく、個々の粒子は本物ではない。**

## Q. `tsconfig` を 2 つに分けたのはなぜか

`lib` から `DOM` を外すと、`document` や `window` が**型として存在しなくなる**。
つまり Core で `document.querySelector(...)` と書いた瞬間にコンパイルエラーになる。

「Core は UI を知らない」を口約束ではなくコンパイラに守らせるための分割である。
View 側だけが `DOM` を持つ `tsconfig.view.json` を使う。

同じことを `test/architecture.test.ts` でも識別子レベルで検査している。
二重に見えるが、守り方が違う（コンパイラは型、テストは文字列）ので両方に意味がある。
