# 画面に出てくる DynamoDB 用語 (2026-08-01)

3D ビューと HUD に出てくる言葉を、**1 本の線で繋いで**説明する。
モデルの実装の話は `summary/` にあるので、ここでは用語だけを扱う。

## まず全体像: すべては「秒あたりの仕事量」の話

DynamoDB の制限は「何 GB 貯められるか」ではなく、**「1 秒あたり何回さばけるか」**で決まる。
用語はこの 1 本の線の上に並んでいる:

```
リクエスト  →  units  →  秒あたりの units  →  キャパシティ  →  足りなければスロットル
 (1 回の書込)   (仕事量)     (需要)              (契約した供給)      (拒否される)
```

以下、この順に説明する。

---

## unit（キャパシティユニット）— 仕事量の単位

DynamoDB は「リクエスト 1 回」を数えない。**サイズに応じた仕事量**を数える。

| | 1 unit で何ができるか |
|---|---|
| 書き込み (write unit) | **1KB** までの書き込み 1 回 |
| 読み取り (read unit) | **4KB** までの強整合性読み取り 1 回（結果整合性なら 2 回） |

だから **「units/秒」と「リクエスト/秒」は別物**である。

```
1KB の項目を書く     → 1 回 = 1 write unit    （1:1 で一致する）
20KB の項目を読む    → 1 回 = ceil(20 ÷ 4) = 5 read units
```

これが `big-item-trap` プリセットの正体:

> 1 パーティションは 3,000 read units/秒 出せる。
> でも 20KB の項目は 1 回で 5 units 食うので、**3,000 ÷ 5 = 600 リクエスト/秒**で頭打ちになる。

「3,000 出るはずなのに 600 で止まった」という事故は、この換算を忘れることで起きる。

---

## WCU / RCU — 契約した供給量

- **WCU** = Write Capacity Unit（書き込みキャパシティユニット）
- **RCU** = Read Capacity Unit（読み取りキャパシティユニット）

「**1 秒あたり** これだけの units を引き受けられるようにしておいて」という**契約値**。

> `40,000 WCU` = 毎秒 40,000 write units 分の書き込みを引き受ける

単位が紛らわしいが、WCU は「秒あたり」を含んだ言葉である（40,000 WCU/秒 とは言わない）。

---

## プロビジョニング (provisioned) — 前もって確保しておくモード

キャパシティの決め方は 2 通りある。

| | プロビジョニング | オンデマンド (on-demand) |
|---|---|---|
| 決め方 | 「毎秒 40,000 WCU」と**自分で申告**して確保する | 申告しない。来た分だけ自動で追従する |
| 課金 | 確保した分（**使わなくても払う**） | 実際に使った分 |
| 向き | 負荷が読める定常的なワークロード | 予測できない・急に跳ねるワークロード |

「プロビジョニング」とは要するに **前もって枠を押さえておくこと**。
コントロールパネルの `プロビジョニング WCU 40,000` は「この枠を押さえた」という意味。

> ⚠️ **よくある誤解**: 「on-demand にすれば無限にスケールするからホットパーティション問題は起きない」
> — 起きる。**1 パーティションの物理上限（後述）は両モードでまったく同じ**である。
> 変わるのは課金と枠の決め方だけ。

---

## パーティション — テーブルを分割して置く物理的な入れ物

テーブルの中身は 1 か所には置かれない。複数の**パーティション**に分けて置かれる。
3D 画面の**柱 1 本 = パーティション 1 個**である。

どの項目がどのパーティションに行くかは、**パーティションキーのハッシュ値**で決まる。
（キー = 項目を識別する値。`user_id` や `tenant_id` など、設計者が選ぶ）

ここに 2 つの上限がある。**この 2 つの区別がすべての鍵**になる。

### 1. 物理上限 (hard cap) — 誰にも越えられない壁

> **1 パーティション = 3,000 read units/秒、1,000 write units/秒**

AWS が決めたハードウェア側の壁。
**お金を払っても、設定を変えても、絶対に越えられない。**

3D 画面の**赤い面**がこの高さ。突き抜けている柱は「もう打つ手がない」状態。

### 2. 頭割りの取り分 (baseline) — テーブルの枠を割り算した値

テーブルに確保した WCU を、パーティションの本数で割ったもの。

```
40,000 WCU ÷ 41 本 = 976 units/秒   ← 1 本あたりの取り分
```

HUD の `頭割りの取り分` がこれ。**プロビジョニングを増やせばこちらは増える**（物理上限とは違う）。

### ホットパーティション

特定の 1 本にトラフィックが集中している状態のこと。
「テーブル全体では余裕があるのに、1 本だけ溢れている」という形で問題になる。

---

## スロットル (throttle) — 容量を超えたら**拒否**される

需要が容量を超えたとき、DynamoDB は**リクエストを失敗させる**。
`ProvisionedThroughputExceededException` というエラーが返る。

> **重要**: スロットルは「遅くなる」ではなく「**失敗する**」。
> ここが Aurora / RDS との決定的な違いで、本プロジェクトが一番伝えたい点。
> - **DynamoDB** = 拒否する（うるさく壊れる。エラー率が上がるのですぐ気づく）
> - **Aurora** = 待たせる（静かに壊れる。エラーは出ず、レイテンシだけが伸びる）

3D 画面では **赤い粒子が弾け散る**のがスロットル。「スロットル率 50%」なら投げた半分が失敗している。

---

## バーストキャパシティ — 使わなかった分の「貯金」

使い切らなかった容量は捨てられず、**最大 300 秒分ためておける**。
忙しくなったときに、その貯金を放出して一時的に取り分以上をさばける。

3D 画面の**台座の色**がこれ。明るい青が満タン、暗いほど残り少ない。

> ⚠️ **これが一番の落とし穴**: 恒常的に容量オーバーしていても、
> **貯金が尽きるまでは完全に正常に見える**（スロットル率 0%）。
> 数分後、貯金が尽きた瞬間に突然壊れる。
>
> `zipf-without-adaptive` プリセットを 60 倍速で見ると、台座が徐々に暗くなり、
> 尽きた瞬間に赤い粒子が出はじめるのが観察できる。
> 「なぜ急に壊れたのか」の答えが、この台座の色にある。

なお貯金を放出している間は、**テーブル全体の実測値が契約した WCU を数分間超える**。
バグではなく、暇な間に貯めた分を使っているだけである。

> 📖 バーストは「なぜ急に壊れるのか」の答えそのものなので、
> 別途 [`260801-burst-capacity.md`](./260801-burst-capacity.md) に詳しく書いた。
> いつ壊れるか・障害がどう広がるか・なぜ負荷を下げても直らないかを、実際の数字で追っている。

---

## アダプティブキャパシティ — 余った取り分を融通する自動機能

暇なパーティションの余った取り分を、忙しいパーティションへ**自動で回してくれる**仕組み。
（現在は常時有効・自動。本アプリでは学習のため ON/OFF を切り替えられるようにしている）

**救える場合と救えない場合がある。ここが山場。**

| 状況 | アダプティブは救えるか | なぜ |
|---|---|---|
| 偏りが**複数のキー**に散っている (`zipf`) | ✅ 救える | 複数のパーティションに分かれているので、余剰を回せば足りる |
| **1 つのキー**に集中している (`singleHot`) | ❌ 救えない | 1 つのキーのデータは**1 つのパーティションにしか置けない**。物理上限 1,000 で頭打ち |

> **単一キーは分割できない。** これが M1 から一貫した本プロジェクトの主題。
> テーブルに 40,000 WCU 積んでも、1 つのキーに集中したら 1,000 で止まる。

### 画面上でアダプティブの効果はどこに出るか

**柱の色は変わらない。** これは仕様である。

色は「需要 ÷ 物理上限」を表しており、アダプティブが変えるのは**通った量**であって
需要ではないため。効果は次の 3 つに出る:

- 内側の実体の柱が**伸びる**（通った量が増える）
- 内側の柱の色が黄色から緑に**戻る**（頭打ちが解消する）
- 赤い粒子が**出なくなる**

---

## 強整合性 / 結果整合性 (consistentRead)

読み取りの種類。書き込み直後の読み取りで何を保証するか。

| | 保証 | コスト |
|---|---|---|
| 強整合性 (consistent) | 常に**最新**の値を返す | 4KB あたり 1 unit |
| 結果整合性 (eventually consistent) | **少し古い値**が返ることがある（通常 1 秒以内に揃う） | 4KB あたり 0.5 unit（**半額**） |

「残高」のように最新でなければ困るものは強整合性、
「いいね数」のように少しの遅れが許されるものは結果整合性、という使い分けになる。

---

## キー分布 (uniform / zipf / singleHot)

トラフィックが**どのキーに向かうか**の型。設計の良し悪しがここに出る。

| | 意味 | 実例 |
|---|---|---|
| `uniform` | 全キーに均等に散る。理想的な設計 | ランダムな UUID をキーにした場合 |
| `zipf` | 一部のキーに偏る。現実的 | ユーザー ID がキーで、一部にヘビーユーザーがいる |
| `singleHot` | 1 キーに集中。**最悪ケース** | 全員の書き込みを `PK = "GLOBAL_COUNTER"` の 1 項目に集約した |

`skew`（zipf の偏りの強さ）を上げるほど上位キーに集中する。
`1 キーへの集中`（singleHot の割合）が 90% なら、全トラフィックの 9 割が 1 キーに向かう。

> なお `uniform` にしても**完全に均等にはならない**。キーはハッシュでパーティションに配られるので、
> 散らし方が理想的でもパーティションごとの負荷にはむらが出る（バグではなくハッシュの性質）。
> `uniform-at-full-capacity` プリセットは、これが原因で 40,000 WCU 積んで 40,000 流すと
> スロットルする、という事実を見せている。

---

## tick — シミュレーション内部の 1 コマ

本アプリ固有の用語。シミュレーションを進める最小単位で、**0.1 秒の仮想時間**。

画面は 60fps で描かれるが、シミュレーションは常に 0.1 秒ずつ刻む。
分けている理由は、フレームレートが揺れても計算結果が変わらないようにするため
（詳細は `knowledge/260801-realtime-3d-view.md`）。

「60 倍速」は tick の幅を変えるのではなく、**1 秒あたりに刻む tick の数**を増やしている。

## 画面のどこを見ればよいか

| 画面の要素 | 表しているもの |
|---|---|
| 柱 1 本 | パーティション 1 個 |
| **外側の半透明な柱**の高さ | そのパーティションへの**需要** (units/秒) |
| 外側の柱の**色** | 需要 ÷ 物理上限。赤いほど壁に近い（青→緑→黄→赤） |
| **内側の実体の柱**の高さ | 実際に**通った量** |
| 内側の柱の**色** | 緑 = 健全 / 黄 = 頭打ち |
| 外と内の**差** | **弾かれた量**（スロットル） |
| **台座の色** | バーストの貯金。明るい青 = 満タン、暗い = 空 |
| **赤い水平面** | 1 パーティションの物理上限。突き抜けたら打つ手なし |
| **シアンの粒子** | 流れ込むリクエスト（サンプリング表示。全部は描いていない） |
| **赤い粒子** | 弾かれたリクエスト |
| 黄色い八面体 | 最も需要が集中している柱の目印 |

## 数字を実際に追ってみる: `single-hot-key`

画面に出ている数字が、どこから出てきたのかを手で追う。

**設定**: 40,000 WCU / 10GB / 項目 1KB / 1 キーに 90% 集中 / 負荷 30,000 req/s

```
① パーティション数
   ceil( 1,000 RCU ÷ 3,000 + 40,000 WCU ÷ 1,000 ) = ceil(40.3) = 41 本

② 1 本あたりの頭割りの取り分
   40,000 WCU ÷ 41 本 = 976 units/秒

③ 需要 (units/秒)
   30,000 req/秒 × 1 unit (1KB なので) = 30,000 write units/秒

④ ホットな柱に向かう需要
   ホットキーの 90% に加え、ハッシュでたまたま同じ柱に乗った他のキーの分も足されて 90.2%。
   30,000 × 90.2% = 27,072 units/秒  ← HUD の「需要 27,072 units/s」

⑤ その柱の状況
   物理上限は 1,000 units/秒。27,072 ÷ 1,000 = 27.1 倍 ← HUD の「物理上限の 27.1 倍」
   通せるのは 1,000。残り 26,072 は拒否
   → 26,072 ÷ 27,072 = 96.3% がスロットル ← HUD の「最も熱い柱のスロットル率」

⑥ テーブル全体では
   残り 9.8% (2,928 units/秒) は他の 40 本に散るので、そちらは全部通る。
   受理 = 1,000 + 2,928 = 3,928 req/秒          ← HUD の「受理 3,928 req/s」
   全体のスロットル率 = 26,072 ÷ 30,000 = 86.9% ← HUD の「テーブル全体のスロットル率」
```

ここで **⑤ の 96.3% と ⑥ の 86.9% の差**が重要である。

> **集計値はホットパーティションを隠す。**
> パーティション数がもっと多ければ差はさらに開き、
> 「全体では数 % にしか見えないのに、そのキーを使っているユーザーからはほぼ全滅」になる。
> CloudWatch の集計値だけを見ていて障害に気づけない事故の正体がこれ。

アダプティブキャパシティを ON にしても、④ の 27,072 は**1 つのパーティションから動かせない**。
だから救えない。40,000 WCU 積んだ意味が、この 1 本に関しては無い。
