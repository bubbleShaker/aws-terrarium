# M4-1: SQS のバックログモデル（Core）

Issue #20 / PR #21。2026-08-04 完了。3D は含まない（M4-2 で別 Issue）。

## 何が手に入ったか

過負荷時の壊れ方に **第 3 の類型「拒否も遅延もせず、ただ溜める」** が入り、三分類が完成した。

| | 過負荷になると | 壁 | 検知できる指標 |
|---|---|---|---|
| DynamoDB | 即座に拒否 | パーティション容量 | エラー率 |
| Aurora | 待たせてから拒否 | vCPU → max_connections | レイテンシ |
| **SQS** | **溜める。何も起きない** | **保持期間 / in-flight** | **`ApproximateAgeOfOldestMessage`** |

同じ 500 q/s を、どれも容量 400 q/s のサービスへ流したとき:

| | 受理 | 拒否 | 症状 |
|---|---|---|---|
| DynamoDB | 400 q/s | 100 q/s | 5 ms 一定 |
| Aurora | 400 q/s | 100 q/s | 2,651 ms |
| **SQS** | **500 q/s（全部）** | **0** | **何も起きない。毎秒 100 件ずつ溜まる** |

窓口数（2）も処理時間（5ms）も容量（400 q/s）も Aurora と完全に揃えてある。
**違いが「入口に壁があるかどうか」だけに絞られる**ようにするため。

## モデルの骨格

```
producer ──▶ [ キュー（無制限） ] ──▶ consumer × c ──▶ 完了
   ↑                  │                    ↑
 壁が無い       壁: 保持期間           壁: 消化レート
 拒否 0         超えたら黙って消える    = c ÷ 処理時間
```

状態は **backlog Q（件）1 つ**。Aurora の待ち行列より単純で、**乱数も Erlang C も要らない**
— producer は待たされないので、窓口のゆらぎが producer 側へ一切伝わらないため。
3 サービス中もっとも強く決定論的になった。

`SqsQueue.step()` の受付側に `Math.min` が 1 つも無いことが、このモデルの主張そのもの。

## 着手前の見立てが違っていた 3 つ

### 1. 年齢を Little の法則で近似すると、警報が逆を向く

`年齢 ≈ Q ÷ 消化レート` は定常状態では正しいが、**過渡状態で動く向きが逆になる**。

| | 過負荷のピーク | 20 秒後（安全域で回復中） |
|---|---|---|
| 実際の最古メッセージの年齢 | 20.0 秒 | **24.0 秒（伸びている）** |
| `Q ÷ 消化レート` の近似 | 25.0 秒 | **20.0 秒（減っている）** |

大小がずれるのではなく、**警報として意味が正反対になる**のが問題の本質。
→ 累積到着量 A(t) を区分線形の折れ線で持ち、FIFO で厳密に逆引きする（`arrivalLedger.ts`）。

節が増えるのは**到着レートが変わった瞬間だけ**なので、負荷ダイヤルを人が回す限り
tick を何万回刻んでも節は数個しか増えない（10,000 tick 流しても節は 2 個）。

### 2. キューの深さの上限は「到着レート × 保持期間」

Issue 起票時は「消化レート × 保持期間」と書いていたが違った。
キューに残っているのは**保持期間ぶんの到着量**そのもので、**消化レートは 1 ミリも効かない**
（それより古いものは捌けたか消えたかのどちらかで、もう居ない）。

到着 500 件/秒・保持 60 秒なら、consumer が 2 個でも 200 個でも上限は 30,000 件。
違うのは**そこへ到達するかどうか**だけ。

### 3. 設定変更のリセット規約が Aurora と正反対になった

| | スケール操作 | 溜まったもの |
|---|---|---|
| Aurora | インスタンスクラス変更 | **リセットされる**（実機がフェイルオーバーを伴う） |
| SQS | consumer 数 / 処理時間の変更 | **持ち越す** |

> Aurora は障害の最中にスケールしても逃げ切れない。
> SQS は溜まったバックログを consumer を増やして掃ける。**それが正しい手**である。

→ `SqsLiveSession.update()` は**どの項目でも作り直さない**。
作り直すのは `replace()`（プリセット）だけ。

## レビューで直したこと（`reviewer` サブエージェント・3 巡）

🔴 must は 3 件。いずれも**教材が嘘をつく**類だった。

1. **`secondsUntilFirstExpiry` が、警報として一番必要な場面で符号を間違えていた。**
   年齢の伸びる速さを `1 − 消化 ÷ 到着` で近似していたが、正しい分母は
   「**先頭が到着した当時の**到着レート」。負荷を安全域へ下げた直後に符号が反転し、
   実際は消失へ向かっているのに猶予の表示だけが消えていた。
   **`ArrivalLedger` が近似を退けた理由そのものを、派生指標で復活させていた**
   → 前 tick との差から実測する（`oldestMessageAgeGrowthPerSec`）
2. **`endToEndLatencySeconds` が「保持期間を超えない」と書きながら超えていた。**
   期限切れがまだ始まっていない過渡状態では分母に期限切れ分が入らず、
   式が `Q ÷ 消化容量` へ退化する。`sqs-retention-cliff` で**消え始める直前
   （画面がいちばん盛り上がる瞬間）に 75 秒**（保持期間 60 秒）が出ていた
3. **直した当の場所の JSDoc に、禁じたはずの閉じた式が残っていた。**
   View が読む公開契約なうえ「年齢が伸びていない ＝ 掃けている」は
   同じコミットで追加したテストが真正面から否定した命題だった

主な 🟡:

- **平衡点の桁落ちで、猶予の表示が 780 万年に化けていた。** 年齢が止まると
  ほぼ等しい 2 数の引き算になり ±5e-13 の揺れが出る。正に振れた tick だけ
  2.5e+14 秒が出て、HUD が「—」と天文学的な数字を数フレームおきに往復する。
  ⚠️ 揺れの振幅は**tick 幅に反比例する**（差を dt で割るため）
- **`update()` の部分適用**で `settings` と `queue` が乖離しうる経路があった
  （途中の setter が例外を投げると「consumer 数だけ新しい」状態で固定される）
- **「送信を止めても年齢は伸び続ける」は一般化しすぎ**だった。成立条件は
  「先頭が、消化レートを上回るレートで積まれた層に居ること」で、
  薄い層まで進めば掃けきる前に縮み始める
- **台帳の防御網が実際には効いていなかった。** クランプが探索の引数にしか
  掛かっておらず、補間の分子が負のまま残っていた（コメントだけが守っているつもりだった）

ε ガードとクランプは、**外すとテストが落ちること**をミューテーションで確認した。
