# M2 完了サマリ — three.js 空間に DynamoDB を投入する (2026-08-01)

Issue #3 / ブランチ: `feat/3-three-js-dynamodb-view`

## 何を作ったか

M1 で数値としてしか見えなかったホットパーティション現象を、**目で見える形にした**。

> ダイヤルで負荷を上げると、1 本の柱だけが赤熱して、頂上でリクエストが赤く弾け散る。
> キー分布を `uniform` → `singleHot` に切り替えた瞬間に絵が変わる。

```
src/
├── core/                       ← M2 で足したのは「駆動」と「配分」だけ。モデルは M1 のまま
│   ├── sim/
│   │   ├── simulationClock.ts  固定タイムステップ。フレームレートと tick を分離する
│   │   └── particleSampling.ts 重みに比例した整数配分 (最大剰余方式)
│   └── scenario/
│       ├── liveSession.ts      インタラクティブ駆動。テーブル再構築の境界を集約
       │                       ※ M3 で dynamoDbLiveSession.ts へ改名（この文書は M2 時点の記録）
│       └── livePresets.ts      M1 の 7 シナリオを空間から選べる形に
└── view/                       ← 新規。Core の状態を読んで描くだけ
    ├── main.tsx / App.tsx      画面全体。React state は「コントロールの鏡」でしかない
    ├── useSimulationDriver.ts  rAF ループ + HUD スナップショットの間引き (10Hz)
    ├── visual.ts               柱の配置・高さ・色（純関数）
    ├── scene/
    │   ├── TerrariumScene.tsx  Canvas・カメラ・物理上限の基準面
    │   ├── PartitionColumns.tsx 柱 (InstancedMesh 3 枚)
    │   └── RequestParticles.tsx 粒子 420 個
    └── ui/
        ├── ControlPanel.tsx    負荷 / キー分布 / アダプティブ / 項目サイズ / 時間倍率
        └── StatusHud.tsx       数字と解説
```

テスト **107 件**（M1 の 84 件 + 23 件）。Core 層は View を 1 行も知らない（`architecture.test.ts` が機械的に検証）。

## 設計上の判断

### 1. `SimulationClock` を View ではなく Core に置いた

`useFrame` の中に累積器を書くのが最短だが、それだと
**「フレームレートが揺れても結果が変わらない」をテストで守る手段が無くなる**。

Core の純粋なクラスにしたので、不規則なフレーム経過秒の列を入力にした単体テストが書ける:

```ts
// 60fps 一定と、4ms〜50ms で揺れるフレーム列で、tick 列が完全に一致する
expect(run(jitteryFrames)).toEqual(run(steadyFrames));
```

### 2. 「テーブルを作り直す / 作り直さない」の境界を `LiveSession` に閉じ込めた

`DynamoDbTable` は設定不変である（コンストラクタでパーティション数もキーの割り当ても確定する）。
したがってキー分布やキャパシティの変更は**インスタンスの作り直し**になる。
この判断を View に散らすと必ず壊れるので、Core 側の 1 箇所に集約した。

再構築の判定は「負荷 (rps) 以外の全フィールド」の安定ハッシュで行う。
個別に列挙すると、設定項目を足したときに追加を忘れて
「変えたのに反映されない」という気づきにくいバグを生む。
残り全部にしておけば、忘れたときの挙動は「余計に作り直す」（安全側）に倒れる。

### 3. シミュレーションの駆動は Canvas の外の rAF ループ

HUD (HTML) と 3D の両方が結果を要る。`useFrame` の中で駆動すると
HUD へ値を持ち上げる経路が必要になり、Canvas の外にシミュレーションが漏れる。

- **3D**: 毎フレーム `session.latest` を直接読む（React の再描画を経由しない）
- **HUD**: 10Hz に間引いたスナップショットを `setState` で受け取る

毎フレーム `setState` すると 50 本ぶんのオブジェクト生成が 60 回/秒 走って落ちる。

### 4. 柱を「外側 = 需要 / 内側 = 通った量」の二重構造にした

**これは実装中に判明した設計上の必然だった。**

赤熱の指標は `utilizationVsHardCap`（= 需要 ÷ 物理上限）と PLAN.md で決めてある。
しかし**アダプティブキャパシティを ON にしても、需要そのものは変わらない**。
つまり色は 1 ミリも動かない。「アダプティブを ON にすると柱の色が変わる」は成立しない。

アダプティブが変えるのは**通った量**である。そこで:

| 表現 | 何を表すか | アダプティブで変わるか |
|---|---|---|
| 外側の半透明な柱の**色** | 需要 ÷ 物理上限（赤熱） | 変わらない |
| 外側の柱の**高さ** | 需要 | 変わらない |
| 内側の実体の柱の**高さ** | 通った量 | **変わる** |
| 内側の柱の**色**（緑→黄） | 頭打ちの度合い | **変わる** |
| 赤い粒子の量 | 弾かれた量 | **変わる** |

内側まで赤くすると全部が赤一色になり、需要と通った量の差が消える。
そのため赤は「需要が物理上限を越えている」ことだけに使い、頭打ちは黄色で示す。

この対応は Issue #3 の受け入れ条件 3（アダプティブ ON/OFF で zipf の柱の色が変わる）を、
**「柱の色」ではなく「内側の柱と粒子」で満たしている**。
`test/liveSession.test.ts` に、需要（= 色）が変わらず受理量だけが変わることを固定するテストを置いた。

### 5. 上限超過ぶんは対数で圧縮する

単一ホットキーでは需要が物理上限の **27 倍**に達する。線形に描くと柱が画面外へ飛び出し、
「他の柱と比べてどれだけ異常か」がむしろ分からなくなる。

物理上限までは線形、超えた分は `log2` を 0.6 倍して圧縮した。
上限を境に伸び方が変わるので、**壁を越えていること自体が形で分かる**。

### 6. tsconfig を 2 本に割った

| | `tsconfig.json` | `tsconfig.view.json` |
|---|---|---|
| 対象 | `src/core` / `src/cli` / `test` | `src/view`（+ 参照する `src/core`） |
| `lib` | `ES2022` のみ | `ES2022` + `DOM` |

Core に DOM の型を渡さないことで、「Core は `window` / `document` を知らない」を
**コンパイラでも**守る。`architecture.test.ts` の識別子チェックとの二重の防御。

## 見えるようになったこと

| プリセット | 空間で何が起きるか |
|---|---|
| `uniform-healthy` | 41 本が同じ高さで並び、粒子が均等に降る。基準面には誰も届かない |
| `single-hot-key` | **1 本だけが基準面を突き抜けて赤熱**。頂上で粒子が赤く弾け散る。他の 40 本は低いまま |
| `zipf-without-adaptive` | 高さがなだらかに偏る。台座（バーストの貯金）が数分かけて暗くなり、**尽きた瞬間に赤い粒子が出はじめる** |
| `zipf-with-adaptive` | 同じ偏りでも内側の柱が伸び、赤い粒子が出ない |
| `big-item-trap` | 読み取りレーンで、20KB 項目のせいで 600 req/s で頭打ちになる |

`zipf-without-adaptive` の「台座が暗くなってから壊れる」が、M1 の発見
**「バーストキャパシティが障害を数分間隠す」**をそのまま画面にしたもの。
60 倍速で 5 秒待てば観測できる。

## レビューで直したこと（記録に残す価値があるもの）

### `replace()` を `update()` に委譲してはいけなかった（🔴）

`update()` はマージなので、省略可能な `initialBurstTokens` が前の設定から**残留**していた。
`big-item-trap`（貯金 0 から始める唯一のプリセット）を見たあとに他のプリセットを選ぶと、
バーストの貯金が 0 のまま始まる。

つまり **`zipf-without-adaptive` の山場（貯金が尽きるまで障害が表面化しない）が、
プリセットを押した順序だけで丸ごと消えていた**。
プリセットの読み込みは無条件の差し替えに変え、リグレッションテストを置いた。

### 率の定義を Core と View の 2 箇所に書いていた（🟡）

`throttleRate` と `burstRatio` を、Core の集計と 3D の描画がそれぞれ手書きしていた。
定義を変えたときに片方だけが古くなる。`partitionMetrics.ts` に 1 つだけ置いて両方から呼ぶ形にした。

### 構造を変えるスライダーはドラッグ中に確定してはいけない（🟡）

WCU や skew を掴んで動かすと `onChange` のたびにテーブルが作り直され、
そのたびに仮想時間とバーストが 0 に戻っていた。つまり**ドラッグ中は一度も時間が進まない**。
掴んでいる間は下書きとして持ち、離した瞬間に確定する `StructuralRange` に変えた。

### 決定論性のガードをテストに追加（🟡）

M2 で「実時間で動かす」経路が初めて入った。実時間に触れてよいのは View の rAF ループだけで、
そこから先は必ず `SimulationClock` を通る。この境界が破られると最も高くつくので、
`Math.random` / `Date.now` / `performance.*` / `setTimeout` を Core の禁止識別子に追加した。

## 積み残し（M3 以降）

- パーティション数の履歴依存（一度増えたら減らない）は未モデル化のまま
- 空間の「探索」（歩き回る）は未着手。M2 は 1 サービス 1 画面に集中した
- テーブルを作り直すと経過時間とバーストがリセットされる。
  UI に `⟳` で明示してあるが、状態を引き継ぐ再構築は将来の課題
- `dist` は 1.1MB (gzip 317KB)。three.js のぶん。M6 の Pages 公開時に分割を検討する
