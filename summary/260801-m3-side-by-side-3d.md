# M3 完了: DynamoDB と Aurora を 1 つの空間に並置する

Issue #9 の残り 2 つの完了条件を満たした。Core は PR #16 までで揃っていたので、
今回は **View（3D と HUD）** と、それを成立させるのに必要だった Core 側の最小限の追加。

## 何が見えるようになったか

### 完了条件 1: スループットは同じなのにレイテンシだけ桁違い

プリセット `same-load-both`（起動時に読み込まれる）。

| | 受理 | 拒否 | 完了 | レイテンシ |
|---|---|---|---|---|
| DynamoDB | 400 q/s | 100 q/s | 400 q/s | 一桁 ms ※ |
| Aurora | 400 q/s | 100 q/s | 400 q/s | **2,651 ms** |

> スループットの数字は完全に同一。違いはレイテンシにしか出ない。

両サービスの容量を 400 q/s にぴったり揃えてあるのが仕掛け
（DynamoDB は WCU 400 / 1KB 項目、Aurora は vCPU 2 × 1/5ms）。
揃っていなければ数字が一致せず、この主張は成立しない。

※ DynamoDB のレイテンシは**このモデルが計算していない**。時間軸の待ち行列を持たないため。
AWS が謳う一桁ミリ秒を参考値として置いており、画面にもそう表示している。

### 完了条件 2: エラーが 1 件も出ないままレイテンシが伸び続ける区間

プリセット `aurora-silent-slowdown`。わずか 5% の過負荷 (420 q/s に対し容量 400 q/s)。

- Aurora は待合室 1,000 席が埋まる **48 秒間、拒否を 1 件も出さない**
- その間にレイテンシは 300ms → 2,651ms へ**単調に伸び続ける**
- 同じ 5% の過負荷を DynamoDB は**最初の 1 秒から**拒否する

HUD が「エラーは 1 件も出ていない。それでもレイテンシは N ms」という警告を出す。
`test/terrariumPresets.test.ts` がこの 48 秒間を tick 単位で固定している。

## 空間の作り

```
                    [源] ← 負荷ダイヤルは 1 本
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
    ▓▓ ██ ▓▓ ▓▓                ╔═════╗ writer
    ▓▓ ▓▓ ▓▓ ▓▓                ║ ▮ ▮ ║ ← vCPU の窓口 (2 本)
       ✦  ✦                    ╚═════╝
   頂上で赤く散る                ∷∷∷∷∷ ← 待合室 (100 席 = 1,000 件)
                               手前で詰まる
```

**1 本のパイプが 2 つへ分岐する**のが決め手。調査で「受理も拒否も同じ数字」と分かった以上、
「同じ負荷を流している」が疑われた時点で主張全体が崩れる。
HUD に「ダイヤルは 1 本です」と書くのは約束事にすぎないが、
目の前で 1 本の管が 2 股に分かれていれば、それは見れば分かる事実になる。

## 実装しないと分からなかった 4 つ

詳細は PLAN.md「M3 の 3D 並置で確定したこと」。

1. **粒子の縮尺は「レート」と「ストック」で 2 系統に分ける** —
   粒子 = 到着レート (共有負荷から導くので両者で必ず一致)、席 = 待ち行列長 Q。
   単位が違うので同じ縮尺には乗らない。両者は Little の法則の両辺 (L と W) を分担している
2. **レイテンシは粒子が待合室を横断する速さで見せる** — 数字を読まなくても、
   Aurora の粒子が這っている間に DynamoDB の粒子が何往復もしているのが見える
3. **負荷ダイヤルの目盛りは有効数字 2 桁の梯子** — 線形では Aurora の帯域 (400 q/s) 全体が
   1 目盛りに潰れ、完了条件 2 にダイヤルが届かない
4. **カメラ距離は要件から逆算する** — 「幅 330px のパネルに隠れない帯へ両方が収まること」と
   「地面から分岐パイプまでが収まること」の厳しいほう。
   係数を手で決めていたら、待合室がコントロールパネルの下に潜った

## 保留していた判断の決着

M2 のレビュー指摘「`DynamoDbSessionSnapshot` / `PartitionView` は View の関心事では」は、
**Core に残すことで確定**した。Aurora 側の HUD を書いて分かったのは、
snapshot が持っているのが `activeSessions` (AAS) / `maxVcpu` (Max vCPU 線) という
**AWS のドメイン語彙**であって描画の都合ではない、ということ。

指摘そのものは正しかったが、違っていたのは**分割線の位置**だった。
線は snapshot の内と外ではなく、「AWS の語彙 / 画面の都合」の間にある。
後者（柱の高さ・粒子の色・席の数）は既に `layout.ts` / `palette.ts` に分離してある。

## レビューで直したこと（`reviewer` サブエージェント）

🔴 must 2 件はどちらも**教材が嘘をつく**類だった。

1. **垂直スケールの説明が事実と逆だった。** 画面に
   「クラスを上げると窓口は 2 → 32 にしかならないが待合室は 1,000 → 5,000 になる。
   垂直スケールで買えるのは主に並ぶ場所の広さである」と出していたが、実際は逆で、
   窓口 16 倍に対し待合室 5 倍。**比は 500 倍 → 156 倍へ改善する**
   （`instanceClasses.ts` の表が正しく書いていたのに、UI 側だけ反転していた）。
   正しい主張は「**どのクラスでも桁が違う**」であって「上げるほど待合室ばかり増える」ではない
2. **`aurora-silent-slowdown` で矛盾する 2 つの判定文が同時に出ていた。**
   「違いはレイテンシにしか出ていない」の判定を**完了量だけ**で行っていたため、
   拒否 20 対 0 という「レイテンシ以外の違い」— しかもそのシナリオの主題そのもの —
   が出ている最中にその文言が表示されていた。拒否量の一致も条件に加えた

主な 🟡:

- `secondsUntilConnectionsFull` を View から Core へ移した（教材の主張を担う数字なので）
- `DrivenSession` の型の穴を塞いだ。`step` を外していたのはセッションだけで、
  `writer` / `table` 経由で `driver.aurora.writer.step(demand, 5)` が**コンパイルを通っていた**。
  モデル本体も投影した型 (`ObservedAuroraWriter` / `ObservedDynamoDbTable`) で返すようにした
- 「同じ負荷なら粒子数が一致する」が実装では成立していなかった
  （DynamoDB は素の需要、Aurora は**再送込みの到着量**で本数を決めていた）。
  Aurora 側も素の需要に揃え、テストを driver を回す形へ書き換えた
  — 元のテストは `f(x) === f(x)` の恒真式で、このずれを検出できなかった
- 席と窓口の**位置**を毎フレーム GPU へ送り直していた（不変なのに）。マウント時 1 回へ
