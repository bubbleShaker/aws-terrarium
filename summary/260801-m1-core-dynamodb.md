# M1 完了サマリ — Core エンジンと DynamoDB パーティションモデル (2026-08-01)

Issue #1 / PR: `feat/1-core-dynamodb-partition-model`

## 何を作ったか

3D 抜きで、**DynamoDB のホットパーティション現象を数値として再現するシミュレータ**。
以降のすべてのサービスモデルが乗る Core 層の土台。

```
src/
├── cli/runScenario.ts          CLI ハーネス (Core の外)
└── core/                       純粋 TypeScript。three.js も React も知らない
    ├── sim/
    │   ├── rng.ts              seed 付き PRNG + 決定論的ハッシュ
    │   ├── tokenBucket.ts      バーストキャパシティ
    │   ├── demand.ts           需要の型 (生成側と消費側の中立地帯)
    │   └── loadProfile.ts      constant / ramp / spike / jitter (合成可能)
    ├── services/dynamodb/
    │   ├── limits.ts           制約値 + 出典と確度のレジストリ
    │   ├── keyDistribution.ts  uniform / zipf / singleHot
    │   ├── partitioning.ts     パーティション数の推定・キーの割り当て
    │   ├── fairShare.ts        max-min fair 配分
    │   ├── allocator.ts        配分戦略 (EvenSplit / Adaptive)
    │   ├── capacityLane.ts     1 レーン (読み or 書き) の容量判定
    │   └── table.ts            テーブル本体
    └── scenario/
        ├── runScenario.ts      シナリオ実行と集計
        └── presets.ts          教材シナリオ 7 本
```

テスト 70 件。うち 2 件は**アーキテクチャ適合テスト**で、
Core 層が View 層のライブラリや I/O グローバルに触れていないことを機械的に守る。

## 設計上の判断

### 固定タイムステップ + 統計モデル + 粒子サンプリング

リクエスト 1 個 = イベント 1 個の古典的な離散イベントシミュレーションは、
10 万 req/s を扱うと 1 秒ぶんに 10 万イベント必要で破綻する。
そこで「時間は固定 tick、数値は統計的に計算、3D では粒子をサンプリング表示」とした。
seed 付き PRNG により決定論的なので、**シミュレータなのに単体テストできる**。

### 3 層の依存を一方向に固定

`Content → View → Core`。Core は上位層を知らない。
口約束は必ず破られるので `test/architecture.test.ts` で機械的に守っている
（実際、CLI を最初 `src/core/cli/` に置いてしまい、レビューで指摘された）。

### 配分方針を Strategy として抽出

アダプティブキャパシティの有無は boolean 分岐ではなく `CapacityAllocator` の差し替えで表現。
`CapacityLane`（消費側）は配分方針を知らないので、
将来 on-demand のプリウォーム挙動などを足すときに触らずに済む。

## 実装して初めて分かった 3 つのこと

計画時には想定していなかったが、教材として最も価値が高いと判断して組み込んだもの。

### 1. 集計値はホットパーティションを隠す

`zipf-without-adaptive` では、テーブル全体のスロットル率は **7.6%** にしか見えない。
しかし 50 本中 1 本は **42.0%** 弾かれている。そのキーを使うユーザーにとっては大障害。

> CloudWatch の集計グラフだけ見ていて障害に気づけない、という事故の正体がこれ。

サマリに必ずパーティション単位の内訳を並べる設計にした。

### 2. バーストキャパシティが障害を数分間隠す

恒常的に容量を超えていても、貯金がある間は**スロットル 0% で完全に正常に見える**。

| 経過時間 | 状態 |
|---|---|
| 0〜約 230 秒 | スロットル 0%。何も起きていないように見える |
| 約 230 秒〜 | 貯金が尽き、スロットル率が跳ね上がる |

観測時間を 60 秒にしていると**この現象を完全に見逃す**。教材シナリオを 900 秒にした理由。

### 3. ハッシュ分散のむらは消せない

キーを完全に均等な重みで設計しても、ハッシュでパーティションへ配る以上むらは残る。

| | 割合 |
|---|---|
| 理想（均等） | 2.44% |
| 実際の最も重い 1 本 | **3.4%** |

結果、40,000 WCU 積んで 40,000 WCU 流すと、最も重い本が物理上限 1,000 WCU に当たって
テーブル全体で 8.3% スロットルする。プロビジョニングに余裕が必要な理由。

## レビューで見つかった重大なバグ

**アダプティブ ON のとき、バーストの貯金が二度と回復しなかった。**

補充量を「アダプティブの配分 − 使用量」で計算していたが、
アダプティブの配分は仕様上**必ず需要以下**になるため、この差は恒久的に 0 だった。
バケットの初期値が満タンなので初回だけ正しく動いて見え、既存テストでは捕まらなかった。

実測（飽和 300 秒 → 完全アイドル 600 秒）:

| | 飽和後 | アイドル後 |
|---|---|---|
| アダプティブ OFF | 29,600 | 150,000（満タンに回復）|
| アダプティブ ON | 29,600 | **29,600（1 も回復しない）** |

貯金が貯まる基準は「**頭割りの取り分 = 払っている分**」であって、
アダプティブで一時的に増えた配分ではない。修正済み、回帰テストあり。

### その修正の副作用で開いた 2 つ目の穴

上記を直したことで、今度は**譲った枠の二重計上**が顕在化した。
アダプティブでは未使用枠が他のパーティションへ再配分されるが、
譲った側が満額の貯金も得ていたため、同じ未使用容量が
「再配分」と「貯金」で 2 回使われていた（貯金額 450,500 → 正しくは 440,000。約 2.3% の過剰）。

### 注意: 「プロビジョニング値の 1.55 倍」はバグではない

修正後も、貯金を放出している間はテーブル全体の受理量がプロビジョニング値を数分間超える
（2,000 WCU のテーブルが 3,100 WCU を 400 秒間）。**これはバーストの定義そのもの**であり、
バグではない。レビュー時にこの数値をバグの証拠と読んだが、実測の結果そうではなかった。

モデルが保証するのは瞬間値ではなく**保存則**である:

> 貯金ゼロから始めた場合、累計の受理量は「テーブルのキャパシティ × 経過時間」を決して超えない。

実測で 800 秒の総受理 1,600,000 units = 総キャパシティ 1,600,000 units と完全に一致。
`test/capacityLane.test.ts` で全パターンを検証しており、
二重計上を復活させる変異を入れるとアダプティブ側だけが落ちることも確認済み。

**実務上の含意**: プロビジョニング値の妥当性を短時間の実測で判断してはいけない。
「2,000 WCU のテーブルで 3,100 WCU 出たから余裕がある」は誤読で、
貯金を切り崩しているだけかもしれない。

## 既知の制限（M2 以降）

- パーティション数の**履歴依存**（一度増えたら減らない）が未モデル化
- バーストの貯金はパーティション単位でしか制限しておらず、
  全パーティションが同時に放出するとテーブルのプロビジョニング値を瞬間的に超える
- tick 履歴は既定 2,000 件へ間引く（15 分のシミュレーションで約 43MB）
